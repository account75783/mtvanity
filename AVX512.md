# Why AVX-512 makes the key search four times faster

mtvanity V1.2. The kernel came with source revision 5, and the prebuilt binaries have it since V1.2.

mtvanity looks for a Meshtastic key whose node ID or public key reads the way you want. Nearly all of its time goes into multiplying 255-bit numbers. AVX-512 has an instruction made for that, and this page shows how the new kernel uses it.

| | |
|---|---|
| Keys per second, 32-core AMD Zen 5 (EC2 c8a) | **6,662 M** |
| Against the AVX2 kernel on the same machine | **4.1×** |
| Keys per second per core | **208 M** |

## What one key costs

Since firmware 2.8 a node ID is the CRC-32 of the node's 32-byte X25519 public key. To test a candidate, the program needs that public key, and getting it is elliptic-curve arithmetic on numbers modulo `2^255 − 19`.

The search does not compute each key from scratch. It walks along the curve in windows of 1,025 neighbouring keys and shares the expensive steps among them. After that sharing, each key costs about:

- **2.5 multiplications and 1 squaring** of 255-bit numbers,
- **one CRC-32** of the 32-byte result,
- **one comparison** against the pattern.

So the speed of the whole program is, to a good approximation, the speed of a 255-bit multiplication.

## Limbs: how a 255-bit number fits in a CPU

No register holds 255 bits, so the number is cut into pieces called limbs. How many limbs you need depends on the widest multiplication the CPU's vector unit offers, because the product of two limbs has to fit in a 64-bit slot with room to add several of them up.

```
AVX2, multiplies 32 x 32 bits: 10 limbs of 25 or 26 bits
|----|----|----|----|----|----|----|----|----|----|

AVX-512 IFMA, multiplies 52 x 52 bits: 5 limbs of 51 bits
|---------|---------|---------|---------|---------|
```

The IFMA instructions (`vpmadd52luq`, `vpmadd52huq`) multiply 52-bit values, so limbs can be twice as wide and there are half as many.

## Half the limbs is a quarter of the work

Multiplying two numbers means multiplying every limb of one by every limb of the other. Halving the limb count therefore divides the number of limb products by four.

| | AVX2 kernel | AVX-512 kernel |
|---|---:|---:|
| Limb products per multiplication | 100 (10 × 10) | 25 (5 × 5) |
| Multiply instructions per multiplication | 100 | 50 |
| Keys served by each instruction | 4 | 8 |
| **Multiply instructions per key, per multiplication** | **25** | **6.25** |

An IFMA product takes two instructions, one for its low 52 bits and one for its high 52 bits, which is why 25 products become 50 instructions. Even so, each key needs a quarter of the multiply instructions it needed before, and fewer additions and carries around them. That ratio is where the measured 4× comes from.

## One multiplication, step by step

With limbs 51 bits apart and products split at bit 52, the two halves of a product land in neighbouring columns: the low half in its own column, the high half worth twice the next one. Columns past the fifth wrap around, because `2^255` equals `19` in this field.

```
column k of the result =
      low halves of column k
  + 2 x high halves of column k-1
  + 19 x ( low halves of column k+5  +  2 x high halves of column k+4 )

then one carry chain brings every limb back under 52 bits
```

Whatever 52-bit limbs go in, each column stays below `2^61`, so nothing can overflow a 64-bit slot. The self-test checks this at the extremes, with every limb of both factors at its largest allowed value.

## Keeping the CPU busy

The multiplication became so cheap that a new problem appeared. A modern core can start the next multiplication long before the previous one has finished, but only if the next one does not need that result. A kernel written as one long chain would leave most of the core idle, waiting. Three arrangements fix that.

- **Four chains instead of one.** A window's 512 table points are multiplied together in four independent runs, so four products are always in flight. One extra step joins them.
- **Both keys of a step side by side.** Each table point gives two keys, one on either side of the window's centre. They are computed together, so neither waits for the other.
- **The inversion done in scalar code.** Each window needs one modular inverse, a chain of 265 dependent steps. Vector lanes cannot shorten a chain, so it is done once, in ordinary 64-bit code, for all eight lanes.

The CRC-32 gains too. It is computed with carry-less multiplications, and the 512-bit form of that instruction handles four keys at a time where the AVX2 kernel handles two.

## Why this program gains more than most

Plenty of software gets little from AVX-512. This workload happens to be close to the ideal case.

- **It is almost pure arithmetic.** Each thread's working data is about 165 KB and stays in that core's cache, so nothing waits on memory.
- **Every key is independent.** Eight in one register never interfere with each other.
- **The hot loop has no unpredictable branches.** A match is a rare exit, not a decision made on every key.
- **The work is exactly what IFMA was built for.** The instructions exist to speed up big-number multiplication in cryptography.

## Measured

Keys per second from `./mtvanity --benchmark`, 2026-11-25.

| Machine | AVX-512 | AVX2 | Scalar | AVX-512 against AVX2 |
|---|---:|---:|---:|---:|
| AWS EC2 c8a, 32 cores, AMD EPYC (Zen 5), Debian 13 | 6,662.5 M | 1,608.9 M | 856.6 M | 4.1× |
| 2 shared cloud cores, Intel Xeon (Emerald Rapids) | 170.8 M | 50.4 M | 29.2 M | 3.4× |

- **Zen 5 gains more than the Xeon.** Published instruction tables say Zen 5 starts two 512-bit IFMA multiplies per clock cycle and Intel's CPUs one, which fits the difference. Over several runs the Xeon averaged about 3.5×.
- **A full 8-digit node ID** takes 4.29 billion keys on average: about 0.65 s on the c8a.
- **A long search ran slower than the benchmark** on the c8a, about 5,700 M keys per second. The cause has not been looked into.
- **For scale,** a 32-thread Intel i9-14900HX laptop, which has no AVX-512, does 516 to 558 M keys per second with the AVX2 kernel.

## Speed that is still checked

The fast kernel is never trusted on its own word.

- **Every hit is recomputed** by a separate, slow, simple X25519 implementation before it is printed. A fault in the fast path can lose a key but cannot print a wrong one.
- **Every search starts with a check** of each kernel against that reference.
- **The kernel was broken on purpose in 47 places,** one at a time. The self-test caught all 47.
- **2,511 keys were re-derived outside the program** by independent Python code, including runs with each kernel forced.

Not yet checked: AMD Zen 4 and any Windows machine with AVX-512. The Windows build of source revision 6 passes its self-test on a laptop without AVX-512, where the kernel stays out of the way. On the Zen 5 instance only the benchmark was reported; its full self-test output has not been seen.

## Which CPUs can run it

The kernel needs AVX-512 F and IFMA, and the 512-bit carry-less multiply (VPCLMULQDQ). The program checks at start-up and each thread keeps whichever kernel is fastest on its own core.

- **AMD:** Zen 4 and Zen 5 (Ryzen 7000 and 9000, EPYC 9004 and 9005).
- **Intel:** Ice Lake, Tiger Lake, Rocket Lake, and Xeons since Ice Lake.
- **Not Intel's 12th- to 14th-generation Core CPUs,** which have no AVX-512. They use the AVX2 kernel at the same speed as before.
